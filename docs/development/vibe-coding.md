# Vibe Coding 开发管理规范

## 1. 目的

本规范用于管理由人确定方向、AI 参与规划和开发的长期项目。目标是在保持快速反馈的同时，让需求、决策、实现、验证和项目状态都可恢复、可审计、可交接。

“Vibe Coding”不代表跳过需求、测试或文档。AI 可以加速实现，但不能替代明确的业务决定和交付证据。

## 2. 当前治理阶段

项目按三个阶段逐步开放 AI 权限：

### 阶段 1：人审核，AI 开发（当前阶段）

- AI 可以起草和拆解 Issue。
- 人决定优先级、验收标准，并将 Issue 移入 `Ready`。
- AI 只能领取 `Ready` Issue。
- AI 完成开发后提交到 `In Review`。
- 人负责最终验收、合并和标记 `Done`。

### 阶段 2：AI 管理辅助，人批量审核

- AI 可以整理 Backlog、识别依赖并提出优先级建议。
- 人批量审核拆解结果和 Ready 队列。
- 开发、验收和合并权限仍与阶段 1 相同。

### 阶段 3：受控 AI Loop

- AI 在人批准的 Loop Mandate 内管理和开发。
- AI 可以连续领取符合授权条件的 Ready Issue。
- L2 工作和 Mandate 外的决定仍需人工处理。
- 未经明确切换，项目始终停留在阶段 1。

## 3. 工作分级

每个 Issue 必须在进入开发前标记风险等级。存在疑问时提高一级，AI 不得自行降低等级。

### L0 快速改动

适用于文案、样式和不影响业务行为的小修复。

- 可以使用简化方案和验证流程。
- 仍需对应 Issue 和基本验证。
- 不得包含数据库、权限、状态、金额或敏感数据变更。

### L1 标准改动

适用于普通页面、接口、查询和非敏感业务功能。

- 必须具有完整开发契约和自动化测试。
- 必须检查管理员与 AI 能力对等。
- 必须通过独立分支和 Pull Request 交付。

### L2 关键改动

以下工作自动归为 L2：

- 数据库结构和数据迁移
- 身份认证、授权和权限模型
- 申请或教师状态流转
- 工资、奖励、扣款和财务数据
- 审计、隐私和数据删除
- 文件访问和安全策略
- AI 委托身份、工具权限和自动执行
- 生产部署、备份、恢复或破坏性操作

L2 必须先完成逐项质询和方案确认，覆盖正常、失败、越权和边界场景，并经过人工验收。

### 优先级与风险等级

优先级表示工作顺序，风险等级表示交付控制强度，两者不能互相替代：

- `P0 紧急`：正在造成严重业务、安全或数据损失，需要立即处理。
- `P1 高`：阻塞当前 Milestone 或关键用户流程。
- `P2 普通`：默认优先级，按 Roadmap 和依赖顺序处理。
- `P3 低`：不影响当前阶段目标的改进或维护。

高优先级不会降低风险要求。例如 P0 的权限问题仍然是 L2，不能为了紧急而绕过人工门禁。

## 4. 项目事实来源

项目使用双层事实来源：

- 仓库文档保存长期有效的产品、领域、架构和流程知识。
- GitHub Issues / Projects 保存动态工作、优先级、依赖和状态。

Git commits 和 Pull Requests 保存实现与审查记录。详细文档分类遵循 [文档管理规范](./documentation.md)。同一信息不得在多个位置重复维护。

## 5. 工作拆解

```text
Milestone
└── Epic Issue
    └── Feature / Bug / Chore / Research Issue
        └── Issue 内的实现 checklist
```

- `Milestone`：一个可发布阶段，例如 POC 或 Recruitment MVP。
- `Epic`：一个完整业务成果，由多个可交付 Issue 组成。
- `Feature`：用户可观察、可独立验收的能力。
- `Bug`：实际行为与已确认预期不一致。
- `Chore`：基础设施、依赖和工程维护。
- `Research`：先获取事实或验证方案，不直接交付生产功能。

普通编码步骤写在 Issue checklist 中。只有能够独立交付、独立验收、存在依赖或需要由不同执行者承担时，才拆成独立 Issue。

每个 Feature 或 Bug 应足够小，使一个 AI 开发回合能够完成或形成明确交接。

## 6. Definition of Ready

Issue 进入 `Ready` 前必须包含：

- 明确的问题或预期业务结果
- 可验证的验收标准
- `In Scope` 与 `Out of Scope`
- 所属 Milestone 或 Epic
- 优先级和依赖关系
- 风险等级 `L0 / L1 / L2`
- 数据、权限、安全和迁移影响
- 管理员能力对应的 AI 查询或操作能力
- 需要更新的长期文档
- 所有阻塞性产品决策均已解决

AI 应通过仓库、代码和工具自行查证事实。缺少业务决定时，AI 每次只提出一个问题并给出推荐答案，等待人确认；不得自行猜测后进入开发。

阶段 1 中只有人可以将 Issue 从 `Human Review` 移到 `Ready`。

## 7. Issue 状态

主流程为：

```text
Draft
→ Human Review
→ Ready
→ In Progress
→ In Review
→ Done
```

辅助状态：

- `Blocked`：存在外部依赖、事实冲突或必须由人决定的问题。
- `Cancelled`：明确不再实施，并记录取消原因。

阶段 1 权限：

- AI 可以创建和完善 `Draft`。
- 人将确认后的 Issue 移到 `Ready`。
- AI 领取 `Ready`，开始后移到 `In Progress`。
- AI 完成并提供证据后移到 `In Review`。
- 人验收、合并后移到 `Done`。
- AI 遇到阻塞时移到 `Blocked`，提出一个明确问题后停止该项工作。

## 8. AI 开发回合

每个开发回合按固定顺序执行。

### 8.1 恢复上下文

1. 阅读 `AGENTS.md`。
2. 阅读 README、领域文档及当前 Issue 链接的长期文档。
3. 检查 Issue、依赖 Issue、当前分支和工作树状态。
4. 区分已有用户改动和本 Issue 改动，不覆盖无关工作。

### 8.2 领取 Issue

1. 确认 Issue 状态为 `Ready`。
2. 确认没有未完成的阻塞依赖。
3. 一次只领取一个 Issue，并将其移到 `In Progress`。
4. 开工前复述目标、范围、验收标准、风险等级和 AI 对等要求。

### 8.3 实现

1. 先理解现有实现和测试，再修改代码。
2. 保持改动聚焦，不顺手处理范围外问题。
3. 业务规则只实现一次，由管理员界面和 AI 工具共同调用。
4. 新发现的问题记录为建议 Issue，不擅自扩大当前范围。
5. 代码事实与 Issue 或文档冲突时停止并交给人决定。

### 8.4 验证与自审

1. 运行风险等级要求的测试、格式、类型和构建检查。
2. 按验收标准逐条收集证据。
3. 检查管理员与 AI 能力对等。
4. 检查权限、审计、错误路径和数据一致性。
5. 执行文档影响检查并更新权威文档。
6. 检查 Diff 是否包含无关改动或敏感信息。

### 8.5 交付

AI 在 Issue 和 PR 中提供：

- 变更摘要
- 验收标准逐条证据
- 测试命令和结果
- 文档影响
- 已知限制和剩余风险
- 人工重点检查项

随后将 Issue 移到 `In Review` 并停止。阶段 1 不得自动领取下一项工作。

## 9. Definition of Done

### L0

- 验收标准全部满足。
- 完成针对性人工或自动验证。
- 没有引入明显的格式、构建或类型错误。

### L1

- 满足 L0。
- 新增或更新相关自动化测试。
- 管理员界面和 AI 能力保持对等。
- 更新受影响的长期文档。
- Issue 或 PR 包含测试命令和结果。

### L2

- 满足 L1。
- 覆盖正常、失败、越权和边界场景。
- 验证权限、审计、数据迁移和回退方案。
- 涉及状态或金额时验证并发和数据一致性。
- 明确列出需要人工重点检查的风险。
- 通过人工验收后才能合并并标记 `Done`。

通用要求：

- 每条验收标准必须附有证据。
- 跳过测试必须写明原因和剩余风险。
- 文档、迁移、AI 工具和审计属于相关功能本身，不是后续补充。
- 只有代码、验证、文档和人工验收全部完成，Issue 才能进入 `Done`。

## 10. Git 与 Pull Request

- L1、L2 使用独立分支：`codex/<issue-number>-<short-name>`。
- 一个分支只解决一个 Issue。
- Commit 使用行为描述并引用 Issue，例如 `feat: add application status transition (#23)`。
- L1、L2 必须通过 Pull Request 进入主分支。
- PR 必须关联 Issue，并包含验收证据、测试结果、文档影响和风险。
- AI 可以创建分支、提交和草拟 PR，但阶段 1 不得自行合并。
- L0 只有在人明确授权后才能直接修改主分支，仍需 Issue 和验证记录。
- 禁止 AI 自行强推、改写共享历史、删除分支或绕过检查。

## 11. GitHub 仓库配置

仓库启用本规范时必须完成以下配置：

- 创建 GitHub Project，并将 `Status` 配置为 `Draft`、`Human Review`、`Ready`、`In Progress`、`In Review`、`Blocked`、`Done` 和 `Cancelled`。
- 创建 `Priority` 字段，取值为 `P0`、`P1`、`P2`、`P3`。
- 创建 `Risk` 字段，取值为 `L0`、`L1`、`L2`。
- Feature、Bug、Chore、Research、Epic 和 Loop Mandate 使用仓库提供的 Issue Forms。
- 保护主分支，禁止强推和删除。
- L1、L2 必须通过 Pull Request，并由人完成最终审核。
- 在测试工具建立后，将相应测试、格式、类型和构建检查设为必需检查。

仓库中的模板文件不会自动创建 GitHub Project 或字段。完成这些设置前，Issue 中填写的状态、优先级和风险等级仍然有效，但必须由人手动维护。

## 12. 管理员与 AI 能力对等

每项管理员业务能力完成时必须同时具备：

```text
管理员界面
+ AI 查询或操作工具
+ 统一业务规则
+ 统一权限校验
+ 完整审计记录
```

AI 不直接访问数据库，也不通过模拟点击管理员页面代替结构化接口。敏感操作可以增加人工确认，但不能成为永久缺失的 AI 能力。

## 13. AI Loop 角色

未来 Loop 模式使用三个隔离的逻辑角色：

- `AI Coordinator`：读取路线图和队列，拆解工作、检查依赖、推荐优先级、分派任务并维护状态。
- `AI Developer`：只针对一个已批准的 Ready Issue 实现、测试并提交 PR。
- `AI Reviewer`：在独立上下文中检查需求符合性、代码风险、测试和文档。

AI Developer 不得批准自己的实现。阶段 1 的最终批准者始终是人。阶段 3 可以让 AI Reviewer 批准 Mandate 授权的低风险工作，但 L2 保留人工门禁。

AI Coordinator 只能在已批准的 Roadmap、Ready 队列和 Loop Mandate 内调度，不能修改产品目标。

## 14. Loop Mandate

AI Loop 默认关闭。只有人审核并批准一份 Loop Mandate 后才能启动。

Mandate 必须定义：

- 目标和所属 Milestone
- 可以处理的 Issue 类型和标签
- 允许自动继续的风险等级
- 最大并行数和在制品数量
- AI 可以创建、修改和关闭哪些 Issue
- 分支、提交、PR 和合并权限
- 必须人工批准的操作
- 停止条件和完成条件

以下情况必须停止并请求人工处理：

- 遇到 Mandate 未授权的风险等级或工作类型
- 需求或验收标准存在歧义
- 代码事实与文档冲突
- 需要破坏性操作、外部付费或生产环境变更
- 测试连续失败且原因不明确
- 发现安全、隐私、工资或权限风险
- 已批准的 Ready 队列为空
- Mandate 目标已经完成

AI 不得扩大 Mandate 范围。范围外改进只能创建建议 Issue，等待人审核。

## 15. 规范变更

本规范是开发管理流程的权威来源。任何变更必须通过 Issue 和 PR，由人审核后生效。`AGENTS.md`、Issue Forms 和 PR 模板是执行入口，不得产生与本文不同的规则。
